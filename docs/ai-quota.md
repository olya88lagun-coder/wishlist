# Защита квоты AI-подбора

Перед первым запросом провайдеру сервер атомарно резервирует дневную квоту и оценку стоимости всех трёх возможных попыток: основной, повторения формата и повторения качества. Блокировка строки дня в PostgreSQL объединяет проверку и резервирование. Старые записи `ai_usage` без `request_id` продолжают учитываться.

После ответа резерв заменяется суммой по полным данным usage. Таймаут, неизвестный расход или сбой сохранения оставляют резерв занятым на этот UTC-день. Потерянный ответ не освобождает потенциально оплаченный запрос. Повторное завершение резерва не меняет уже записанную сумму.

## Лимиты и доверенный прокси

- Существующие лимиты гостя и аккаунта сохраняются.
- Гости дополнительно делят лимит сети. `AI_DAILY_LIMIT_GUEST_NETWORK` по умолчанию равен `AI_DAILY_LIMIT_GUEST`; пустое значение использует этот предел, `0` запрещает гостевые запросы сети.
- Несколько гостей за одним IPv4 или IPv6 /64 используют общую квоту. Вход в аккаунт использует лимит аккаунта.
- Сеть сохраняется как HMAC с `SESSION_SECRET`, без исходного IP. IPv4-mapped IPv6 нормализуется, остальные IPv6 объединяются по /64.
- Код доверяет последнему адресу `X-Forwarded-For`. Это предполагает текущую схему публикации: web без открытого порта, Caddy как последний входной прокси. При изменении этой схемы нужно повторно проверить доверие к заголовку. Пустой или неверный адрес попадает в общий ограниченный bucket.

## Публикация и ограничения

Миграция `0008_ai_quota_reservations.sql` создаёт две таблицы и nullable-связь `ai_usage.request_id`. Исторические записи не удаляются. Текущий deploy запускает миграции до перезапуска web; новый обработчик нельзя запускать до этой миграции.

Суммы рассчитываются по настроенным тарифам модели. Резерв использует размер сериализованного запроса с запасом и двойной выходной предел. Это консервативная оценка, а не сверка счёта провайдера. Изменение тарифа требует обновления конфигурации цен.

Локальные проверки используют PGlite и подменённый `fetch`. Проверена конкуренция вызовов внутри одного движка, но отдельный нагрузочный тест на независимых соединениях PostgreSQL и сверка платного production usage не проводились.
